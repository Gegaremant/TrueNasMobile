# Тестирование

Как проверять TrueNasMobile и почему проверок такого рода недостаточно — история
одного бага, который прошёл всё, кроме запуска на устройстве.

---

## 1. Почему этот документ существует

1.0.2 собрался, прошёл `lintVitalRelease`, прошёл все тогдашние 27 юнит-тестов,
прошёл проверку целостности APK — и **закрывался на каждом устройстве сразу после
успешного входа по паролю**. Ошибка была `getBackStackEntry` на графе, который
не регистрирует маршрут; бросалась она в композиции, до первого кадра, поэтому
пользователь видел просто «приложение закрылось».

Ни одна из проверок того дня не могла это увидеть: ни компиляция, ни линтер, ни
юнит-тесты не выполняют Compose-навигацию. Вывод, который стоит за всеми
изменениями ниже: **проверка, которая не может увидеть класс ошибок, не должна
создавать ощущения, что она его покрывает.**

## 2. Что есть сейчас

### 2.2 Robolectric

`NavHostOwnershipRuntimeTest` — единственный набор, которому нужен Android
runtime. Он поднимает настоящие `NavHost`, настоящие `NavHostController` и
вызывает настоящую функцию `dashboardViewModelOwner`. Это принципиально: ошибка,
которую он ловит, существует только в момент, когдаlookup происходит.

Три вывода, которые пришлось учесть при его написании — они же пригодятся, когда
вы будете писать следующий Robolectric-тест:

1. **Нужен базовый `Application`.**
   `@Config(application = android.app.Application::class)`. Настоящий
   `TrueNasMobileApplication` в `onCreate` ставит задачу WorkManager, а
   WorkManager отказывается инициализироваться, если Application не
   `Configuration.Provider`. Тест навигации не должен это наследовать. Это же
   означает, что **любой** Robolectric-тест, которому понадобится
   `TrueNasMobileApplication`, сначала упрётся в эту стену — см. раздел 6.
2. **`navigation-testing` не нужен и вредит.** Его `TestNavigatorProvider`
   конфликтует с `ComposeNavigator`: `ClassCastException`. `TestNavHostController`
   в 2.9.8 вообще не имеет публичного `setGraph`. Обычный `NavController` +
   `TestLifecycleOwner` + `setViewModelStore` работает и честнее.
3. **Строить граф руками через `destination(...)` — тупик.** `composable`-
   destinations требуют Compose-навигатор, который регистрирует только сам
   `NavHost`. Поэтому в тесте рендерится настоящий `NavHost`.

### 2.3 Проверка артефактов

`ReleaseArtifactTest` делает то, что раньше делалось руками при каждом релизе:

- **CRC каждой записи ZIP.** Оборванная загрузка ставится без ошибки, а падает
  при запуске.
- **Adler-32 и SHA-1 из dex, пересчитанные так же, как это делает ART:**
  Adler-32 — с offset `0x0C` (то есть включая поле подписи), SHA-1 — с `0x20`.
  Область Adler-32 легко перепутать, и ошибка выглядит как битая сборка: первую
  версию теста накрыло переполнение `Int` в `s2`, и она «нашла» поломку в
  совершенно исправном APK.
- **Размер dex в заголовке против размера в архиве.**
- **SHA-256** — печатается в stdout, оттуда попадает в заметки релиза.

Тест пропускается (`Assume`), если APK не собран: это гейт релиза, а не причина
падать `./gradlew test` на чистой машине.

### 2.4 Smoke-тест на устройстве

```bash
scripts/smoke-device.sh                    # собрать, поставить, запустить
scripts/smoke-device.sh --apk path.apk     # готовый артефакт
scripts/smoke-device.sh --timeout 90       # дольше ждать
```

Скрипт проверяет CRC, ставит APK, чистит logcat, запускает и **следит, что процесс
жив**. Отдельно ловится «тихая смерть» — процесс исчез, а `FATAL EXCEPTION` не
залогирован. Это ровно та сигнатура, что была у 1.0.2: падение раньше, чем
фреймворк успевает сообщить об ошибке.

Честно о статусе: **скрипт написан и проверен синтаксически, но на этой машине
нет `adb`, поэтому успешный сценарий не прогонялся.** Первый прогон с реальным
устройством — за вами. Он ничего не автоматизирует по логину: вход всё равно
делается руками, скрипт лишь следит, что приложение не умерло.

### 2.5 Гейт релиза

```bash
./gradlew :app:verifyRelease
```

Собирает релизные APK, после них гоняет весь набор юнит-тестов (включая проверки
артефактов) и `lintVitalRelease`. Порядок «сначала сборка, потом тесты» задан
`mustRunAfter`, а не угадан.

В CI то же самое происходит в `.github/workflows/build.yml`: **тесты → линт →
сборка → проверка артефактов → подпись → публикация**. До 27 сентября релизный
воркфлоу не делал ничего из этого и публиковал по тегу что собиралось. Именно
так уехал 1.0.2.

## 3. Чего тесты не ловят

Честный список, чтобы не считать покрытым то, что не покрыто:

- **Поведение за логином.** Ни один тест не входит в учётную запись и не жмёт
  кнопки. Интерактивных тестов (androidTest) нет: на этой машине нет устройства,
  и писать непроверяемый код — значит отдать его вам непроверенным.
- **Поведение против живого TrueNAS.** Все ViewModel работают с настоящим
  `TrueNASApiManager`, который открывает WebSocket. Сетевых тестов нет, и для них
  понадобился бы настоящий сервер или подставной транспорт.
- **Фоновые задачи и виджеты.** `AlertWorker`, `AppsRefreshWorker`, Glance-виджеты
  и активности виджетов не имеют тестов. В частности, тот самый «прогрев чужих
  NAS» из `warmOtherProfiles` открывает реальные сокеты.
- **Рендер и вёрстка.** `MPAndroidChart`, графики производительности, анимации.
- **Классические баги Compose-навигации в целом.** Закрыт конкретный класс
  (владение графом), а не весь класс «Compose-ошибок, которые видны только на
  устройстве».

## 4. Правило для новых тестов

Тест, который нельзя заставить упасть, не считается тестом. Каждый новый набор
следует проверять так:

```bash
# 1. внесите правку, которую тест обязан поймать
# 2. убедитесь, что сборка красная и в сообщении видно ИМЯ проблемы
# 3. откатите правку, убедитесь, что сборка зелёная
```

Так проверены все наборы этого документа: `NavHostOwnershipTest` ловит
переименование параметра в `dashboardViewModelOwner`, `RouteRegistrationTest` —
переход на незарегистрированный маршрут, `AppCacheLifecycleTest` — удалённую
строку очистки, `ReleaseArtifactTest` — испорченный Adler-32.

## 6. Что стоит сделать дальше

- **Сделать `TrueNasMobileApplication` пригодным для Robolectric.** Сейчас
  приложение нельзя поднять в тесте: `onCreate` ставит задачу WorkManager, а для
  этого нужен `Configuration.Provider`. Перевод на on-demand инициализацию
  WorkManager (рекомендованный самой библиотекой способ) уберёт препятствие и
  заодно даст контроль над моментом инициализации в проде. Не сделано здесь,
  потому что это изменение поведения при старте, а не тестовая правка.
- **Подставной транспорт для `TrueNASClient`.** Сейчас сетевой слой
  неинъецируемый: `TrueNASApiManager` создаётся с живым `TrueNASClient`. С
  интерфейсом поверх сокета ViewModel'ы можно тестировать без сервера — и
  закрыть самый большой пункт из раздела 3.
- **Интерактивные тесты** (androidTest) для пути «вход → дашборд», когда
  появится устройство в CI (или эмулятор на runner'е).
- **Тест на `AccountSessionRegistry`** с подставным менеджером: у него есть
  нетривиальная ветка с `core.ping` для протухшей записи, и она ничем не
  прикрыта.
